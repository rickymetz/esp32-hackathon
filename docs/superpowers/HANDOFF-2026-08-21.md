## NOT verified — the honest list

- **`app_registry_invalidate()`'s unmount-failure path.** Only reachable by tapping
  **Refresh**, which cannot be driven over serial. This is the C2 fix. It is compile-correct
  and reviewed, but the failure path has never executed.
- **Three Refresh interactions**, all needing a finger: Refresh with the card present;
  Refresh during an in-flight push; eject → Refresh → reinsert → Refresh.
- **C1 boot-time race (reset-during-rescan): INCOMPLETE and possibly a real bug.** The run
  wedged the board at reset 7 of 14. Cause is genuinely ambiguous — the harness pulses RTS
  to reset, which may have glitched the USB strapping, *or* the boot-time list build may
  have crashed under a concurrent rescan. **Retest one pulse at a time before trusting it.**
- **Regression sweep (`counter`, `tick_test`, `hook_bypass`, `broken`, `headless`,
  `input_test`) did not run** — blocked by that wedge.

## Open issues

1. **Coroutine escape.** A `while true do end` inside `coroutine.wrap` is not reachable by
   the Lua interrupt hook — `lua_newthread` starts with `hookmask == 0`. It falls through to
   a watchdog reboot (~10 s) into a working launcher. Bounded and documented, not closed.
   Proper fix is wrapping `coroutine.create`/`wrap` to install the hook on new threads.
2. **`obj:delete()` mid-run** does not free its object record until app exit. The per-launch
   leak is fixed; this residual is not.
3. **Failed `rename()` leaves `.push.tmp`** on the card. Pre-existing, harmless, uncleaned.
4. **No file CRUD over serial.** `PUSH` is create/update only — no `LIST`, `GET` or `DELETE`,
   and `push.py` rejects anything but `.lua`. Consequences: scratch files can only be removed
   with a card reader, and **TTF fonts and WAV audio cannot reach the card at all**, which
   blocks the design guide's hero-text guidance and Phase 3 audio. Scoped at roughly half a
   day for full CRUD plus arbitrary file types; a `LIST` + `DELETE` subset is ~2 hours.
5. **~7 scratch apps on the SD card** (`pushed.lua`, `racetest.lua`, `stress_c1.lua`,
   `boot_push.lua`, `c2_test1/2.lua`, `c2_check_tmp.lua`) — need a card reader, see item 4.

## Constraints worth not rediscovering

- **`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0` is global.** Plain `malloc()` now prefers PSRAM,
  because ESP-IDF otherwise pins every sub-16 KB allocation internal — exactly LVGL's widget
  size class. **Any DMA or radio buffer must ask for `MALLOC_CAP_INTERNAL` explicitly.**
- **Internal DRAM is the scarce resource**, not flash and not PSRAM. Budget from **198,767**
  bytes once both radio stacks are compiled in (they cost ~74 KB static), and watch
  *largest contiguous block*, not free total — that is what Wi-Fi and TLS actually need.
- **Register capability modules from a one-time `*_register()`**, never from `luaopen_*`,
  which runs per app launch and overflows an 8-slot global cleanup table.
- **Never hand out a pointer into shared state.** `app_registry_get()` was deleted for this
  after it caused a NULL-deref race. Accessors return copies.
- **Lock order:** `s_app_mutex` (outer) → `bsp_display_lock` → registry lock (inner), and no
  module lock is ever held across a callback into `launcher_main.c`.
- **Any error path that can unwind out of an LVGL binding must call
  `lua_lvgl_force_unlock_if_held()`.** Missing it on *one* of five catch sites left both LVGL
  locks held and wedged the board with no software recovery — this is the bug that most
  likely caused the mid-session wedge.
- **`LUA_32BITS=1` is set build-wide** in `launcher/CMakeLists.txt`. A per-component copy is
  wrong; getting it inconsistent aborts in `luaL_checkversion_` with no useful message.

## Process notes

- **The board is a single lock.** Two agents flashing at once produced a reboot storm and an
  invalidated verification run. Do not flash while the tree is dirty with someone else's
  edits — a build would compile their work in progress.
- **Recovering a wedged board:** hold PWR ≥ 6 s → hold BOOT → press PWR → release BOOT →
  reflash → power-cycle again. No software reset recovers it; all five `esptool --before`
  modes fail. If the *firmware* is fine and only USB is hung, a plain power cycle is enough.
- **Agents have repeatedly misreported the board as absent** when it was enumerated and
  healthy — verify with `glob('/dev/cu.usbmodem*')` before believing it.
- **Verify claims against current files.** Several agents were served a stale cached copy of
  `docs/APP_CONTRACT.md` and "confirmed" a divergence that did not exist.
